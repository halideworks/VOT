# QUIC pump validation, 2026-09-07

The pump now services quiche timers after every bounded receive pass, including
passes that receive packets. Previously only an empty receive wait serviced
timers, so a continuously nonempty queue could starve recovery and draining.
It also retains a parked packet's release time across receive wakeups, rather
than treating any wakeup as permission to send that packet early. Shutdown
still flushes the packet best effort, and normal sending retains the existing
pacing quantum.

Two overhead reductions accompany these fixes: iterate quiche's owned readable
stream snapshot directly instead of collecting it into another vector, and
collect connection statistics once per sample instead of four times. In the
pinned quiche source, collecting those statistics scans all stream send buffers.
No congestion algorithm, flow-control window, verification, or FEC policy changed.

## Method

One isolated ASCII large VM, eight vCPUs, 16 GiB RAM, Intel Xeon Skylake,
Linux 6.8.0-117-generic. Both endpoints ran on that VM. Source and destination
were on its ext4 disk; the source was reused from page cache. Each fresh
destination received one 2 GiB zero-filled object with BLAKE3 verification.
Every accepted run had exit status zero and reported exactly 2,147,483,648
verified bytes and root
`355704d9f4d00326c3b32d6b83035e997489ddb7ef2a50df37d4a16ec9f992a6`.

Both binaries used Rust 1.97.1, the normal release profile, `vot-cli --features
wire`, and quiche revision `ce7e5b71f3198125ab92a1626390bbe3a2c7faa0`.
The baseline includes the preceding coverage and mounted-share changes.
The changed binary adds the pump changes described above; unrelated intervening
Windows-only lint edits do not affect these Linux binaries.

- Baseline SHA-256: `c3499a48d06c579c293de2975fea439de5a65c29b5ee2ab28a3623637f34c503`.
- Changed SHA-256: `468606d22311083eb5d979cb81215c24e3c0964e05031d57df694948900d61a4`.

The matrix uses one and eight loopback rails with `VOT_DATAGRAM_FEC=off`;
WAN emulation uses eight rails and `VOT_DATAGRAM_FEC=auto`. The isolated veth
pair has MTU 1500, UDP segmentation enabled, 50 ms netem delay in each
direction, 2 Gbit/s rate, queue limit 200,000, and either zero or 3% random
loss in each direction. Socket buffer caps were 64 MiB on the test VM.
Congestion control was the existing default, unpaced BBR2. No live network
or storage configuration was changed.

Pairs ran sequentially with alternating arm order. Transfer times come from
`VOT_FETCH_STATS=1`, excluding process launch and the separate profiling run.
Results were streamed to local storage as each run finished.
The raw logs, profile, and exact rig scripts were archived locally before
requesting deletion of the temporary VM.

## Results

All 32 transfers passed, totaling 64 GiB of verified payload. Times are ms;
ranges show the smallest and largest samples. The
[CSV](quic-pump-2026-09-07.csv) retains every sample and both endpoints' CPU time.

| Path | Pairs | Before median (range) | After median (range) | Time change |
| --- | ---: | ---: | ---: | ---: |
| Loopback, 1 rail | 3 | 2552 (2514-2614) | 2614 (2591-2653) | +2.4% |
| Loopback, 8 rails | 7 | 2590 (2511-2798) | 2555 (2416-2858) | -1.4% |
| 100 ms RTT, 2 Gbit/s, no loss | 3 | 10433 (10403-10515) | 10316 (10287-10378) | -1.1% |
| 100 ms RTT, 2 Gbit/s, 3% loss each way | 3 | 11578 (10594-12221) | 10884 (10686-11809) | -6.0% |

The first three eight-rail pairs suggested a 10% improvement. Four additional
pairs reduced it to 1.4%, with strongly overlapping ranges. No reliable
throughput gain is established. The lossy samples overlap substantially too;
their completion is useful regression evidence, not a speed claim. FEC was
offered automatically in the emulated WAN cells but no generations were coded.

The Linux workspace passed 1,518 tests with wire enabled, with 12 ignored.
The live QUIC suite passed 107 tests on each of Linux and native Windows,
with one ignored on each. Deny-warnings clippy passed for the wire-enabled
Linux workspace and native Windows QUIC crate. The new finite-input timer
test catches starvation without hanging; pacing checks cover repeated early
wakes, release at the horizon, already-expired releases, and shutdown flushing.

## Profile and remaining work

A separate baseline eight-rail loopback profile sampled both endpoints at
499 Hz. It attributed 9.68% of samples to `rwsem_spin_on_owner`, predominantly
under ext4 positional writes, 9.13% to BLAKE3's AVX-512 hashing routine, and
5.08% to AES-GCM in the listener's pump alone. These are samples on this VM,
not portable CPU-cost estimates. The profile does not support treating pump
bookkeeping as the only remaining throughput bottleneck.

Native Windows UDP offloads remain a separate optimization opportunity: VOT's
current segmented send/receive implementation is Linux-only. Windows supports
[UDP segmentation offload](https://learn.microsoft.com/en-us/windows-hardware/drivers/network/udp-segmentation-offload-uso-),
but adopting it needs native adapter measurements and tests for fallback,
packet boundaries, and shared-socket behavior. It is not implemented by this
change. Ext4 write contention is another measured target; bypassing verification
or durability checks is not a proposed optimization.

These tests do not establish a fastest-product claim, a real WAN throughput
claim, or performance under prolonged high loss, competing flows, or server
power loss.
