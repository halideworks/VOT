# ADR-0039: the datagram FEC erasure code is Cauchy Reed-Solomon over GF(2^8)

Status: Accepted

## Context

The architecture places experimental datagram FEC after the relay work, before
VCRC and multipath. It freezes the field as GF(2^8) and the initial geometry as
64 source symbols with a repair cap of 16 (architecture section 9). It registers
the `DATAGRAM_FEC` extension and five experimental frames but does not say
which code produces a repair symbol or how a receiver reconstructs a lost one.

Any code the project adopts must be written from public specifications with
independent vectors (`DEPENDENCIES.md`, `PATENTS.md`), must bound every
allocation before it happens, and must be small enough to sit in the audited
correctness core. The datagram carrier is lossy and unordered, so the code must
recover from erasures at known positions, not from corrupted bytes; datagram
integrity is the carrier's job.

## Decision

**Datagram FEC uses a systematic Cauchy Reed-Solomon erasure code over
GF(2^8), with the polynomial 0x11D and generator 2, exactly as written in
`spec/fec.md`.**

- Source symbols are sent unchanged as ESIs `0..k-1`; repair symbol `i` is the
  Cauchy row `inverse((k + i) XOR j)` applied to the sources.
- Any `k` received symbols of a generation reconstruct all `k` sources. Fewer
  than `k` is `INSUFFICIENT_SYMBOLS` and reconstructs nothing. A symbol with
  an ESI outside the geometry or a length other than `L` fails the whole call
  as `INVALID_SYMBOL`; nothing is silently dropped.
- Geometry is `(k, r, L)` with `k` in `1..=64`, `r` in `0..=16`, `L` in
  `1..=65535`. Anything else is `INVALID_GEOMETRY`, checked before allocation.
- Decoding is deterministic: received sources first, then repair ESIs in
  ascending order, then Gauss-Jordan elimination.
- The code is implemented in-tree, in safe Rust, with no new dependency. Its
  vectors are generated by an independent Python implementation of the spec
  text and validated in CI.

Cauchy was chosen over the RFC 5510 Vandermonde construction because it is
systematic by construction, needs no matrix preprocessing, and its invertibility
argument is one sentence. Fountain codes were not chosen: at 64 source symbols
the linear-algebra cost is negligible and a maximum-distance-separable code
gives exact recovery guarantees the credit accounting can reason about.

Frame payloads for `CODING_EPOCH_OPEN`, `GEN_STATE`, `GEN_DONE`,
`CODING_EPOCH_CLOSE`, and `DATAGRAM_CREDIT`, and the datagram symbol header,
are not fixed here. They follow in the wire integration ADR once the code and
its crate exist.

## Consequences

- One repair symbol costs one GF(2^8) row multiply per byte of `L`; a full 64/16
  generation is 1024 row-byte products per byte of symbol length, well inside
  the CLI's per-symbol budget on the wire path.
- The decoder holds at most one generation of `k` symbols plus a `k x k` matrix.
  Receiver credit caps active generations, so memory is bounded by the geometry
  a receiver accepted.
- Changing the field, polynomial, or matrix is a new code and needs a new
  extension identifier; version zero of the vectors is frozen.
- The extension is offered by default. Local path-loss policy enables coding;
  clean traffic stays on the reliable path.
